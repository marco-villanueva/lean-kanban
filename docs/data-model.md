# Data Model

Lean Kanban persists four domain entities in SQLite:

~~~text
Board 1 --- N Column
Board 1 --- N Issue
Column 1 --- N Issue
Issue 1 --- N Comment
~~~

All primary keys are text UUIDs generated by the application.

## Boards

Table:

~~~sql
CREATE TABLE boards (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
~~~

Semantic fields:

| Field | Meaning |
| --- | --- |
| id | Internal board UUID |
| name | Board display name |
| description | Optional context |
| created_at | ISO timestamp |
| updated_at | ISO timestamp |

Validation:

- name required;
- name trimmed;
- max name 120;
- description max 2000.

The board list endpoint also calculates columnCount and issueCount dynamically. These are response metadata, not stored columns.

## Columns

Table:

~~~sql
CREATE TABLE columns (
  id TEXT PRIMARY KEY,
  board_id TEXT NOT NULL REFERENCES boards(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  color TEXT NOT NULL DEFAULT '#64748B',
  position INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
~~~

Validation:

- name required;
- name max 80;
- color must be #RRGGBB.

Position is zero-based within a board.

Deleting a board cascades its columns.

### Column deletion semantics

Deleting a column is intentionally guarded when issues exist.

Callers must choose:

~~~text
mode=move
~~~

with targetColumnId, or:

~~~text
mode=delete
~~~

to delete issues as well.

This avoids silent data loss.

## Issues

Logical current table:

~~~sql
CREATE TABLE issues (
  id TEXT PRIMARY KEY,
  board_id TEXT NOT NULL REFERENCES boards(id) ON DELETE CASCADE,
  column_id TEXT NOT NULL REFERENCES columns(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  description TEXT DEFAULT '',
  color TEXT NULL,
  position INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
~~~

The base CREATE statement predates issue color, so migration adds color through ALTER TABLE when needed.

Validation:

| Field | Rule |
| --- | --- |
| title | required, trimmed, max 200 |
| description | max 8000 |
| color | null or #RRGGBB |
| position | integer >= 0 for move requests |

An issue stores both board_id and column_id.

The board reference makes board-wide issue queries direct and explicit.

The column reference determines status.

## Comments

Table:

~~~sql
CREATE TABLE comments (
  id TEXT PRIMARY KEY,
  issue_id TEXT NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  content TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
~~~

Validation:

- non-empty after trim;
- max 4000.

There is no author field because there is no user system.

Deleting an issue cascades its comments.

## Indexes

Current indexes:

~~~sql
CREATE INDEX idx_columns_board
ON columns(board_id, position);

CREATE INDEX idx_issues_column
ON issues(column_id, position);

CREATE INDEX idx_issues_board
ON issues(board_id);

CREATE INDEX idx_comments_issue
ON comments(issue_id);
~~~

These match current access patterns.

## Ordering

### Columns

Column order is stored as integer position within a board.

A reorder request sends the complete desired column ID list.

The API verifies that every board column appears exactly once.

It then writes:

~~~text
first  -> 0
second -> 1
third  -> 2
~~~

### Issues

Issue position is relative to its column.

Moving an issue performs these steps conceptually:

1. Load the issue.
2. Validate the target column belongs to the same board.
3. Remove the issue from its old ordering.
4. Renumber old-column items.
5. Load target-column items excluding the moving issue.
6. Clamp requested target position to a valid index.
7. Insert the moving issue.
8. Renumber target ordering.
9. Update issue column_id and updated_at.

The entire operation runs in a transaction.

## Timestamps

Timestamps are ISO strings.

updated_at is refreshed for direct entity updates and important move/reorder operations.

The project does not currently maintain a full activity log.

## Colors

Columns always have a color.

Default:

~~~text
#64748B
~~~

Issues may have:

~~~text
null
~~~

which means no explicit issue accent.

Colors are visual metadata only. They have no workflow semantics.

## Portable IDs versus internal IDs

SQLite IDs are internal UUIDs.

Full Kanban JSON uses portable IDs such as:

~~~text
col-0-todo
issue-0-draft-copy
~~~

These IDs exist only inside the export format to preserve references between exported records.

Import creates fresh internal UUIDs.

Therefore:

- do not expect a Full JSON round-trip to preserve database UUIDs;
- compare semantic content instead of internal IDs in tests.

## Cascades

Current foreign-key cascades:

~~~text
delete Board
  -> columns deleted
  -> issues deleted
  -> comments deleted

delete Issue
  -> comments deleted
~~~

Deleting a Column directly also cascades issues because of the foreign key, but the REST API protects this operation with explicit mode selection when issues exist.

## Concurrency assumptions

Current model assumes:

- local single-user operation;
- low write concurrency;
- no realtime collaborators.

There are no optimistic concurrency tokens, locks, version fields or conflict-resolution algorithms.

If real multi-user concurrent editing becomes a requirement, that should trigger a separate architecture decision rather than being prebuilt now.
